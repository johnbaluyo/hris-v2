# 01 Authentication and authorization

## Purpose and sources

Authenticate employees and applicants, provision accounts, control module actions and record access, and establish trusted partner login. **Observed** describes the existing code; **target** describes the replacement; **unresolved** requires an explicit decision.

- [LoginController](../../../app/Http/Controllers/Auth/LoginController.php): `customLogin`, `ssiLogin`, inherited `AuthenticatesUsers`, and legacy attendance methods.
- [RegisterController](../../../app/Http/Controllers/Auth/RegisterController.php), password reset/confirmation/verification controllers in the same directory.
- [User](../../../app/User.php): credentials, role/employment attributes, account/profile mutations and approver lookup.
- [web routes](../../../routes/web.php), [API routes](../../../routes/api.php), [HTTP kernel](../../../app/Http/Kernel.php), [auth config](../../../config/auth.php), [session config](../../../config/session.php).
- [AuthServiceProvider](../../../app/Providers/AuthServiceProvider.php), [sidebar](../../../resources/views/partials/_sidebar.blade.php), [staff editor](../../../resources/views/hr_staff/staff_modal.blade.php), [API token middleware](../../../app/Http/Middleware/VerifyApiToken.php).
- [Integration contracts](../INTEGRATION_CONTRACTS.md) for exact SSI and bearer-auth protocols.

## Observed identities and roles

| Legacy value | Meaning in source | Migration concern |
| --- | --- | --- |
| `user_type = 0` | Applicant | Stored in the same `users` table as employees |
| `1` | Staff | Often paired with employment type checks |
| `2` | Division Chief | Division and particular job titles affect routing |
| `3` | Human Resource | Several controllers check it; no general policy layer enforces all actions |
| `4` | Executive Director | Special overview and approval paths |
| `5` | Admin in staff editor and initial migration comment | Not the admin value used by the sidebar branch |
| `6` | Admin in sidebar comment/branch | Not offered by the same staff editor; resolve D02 |

`employee_type` is separate from role: staff options include `Permanent`, `CSW`, `Contractual Regular`, `Probationary`, and `Intern`; applicants use `Applicant`. Archive status, termination date, position, division, OIC delegation and hardcoded account exceptions are additional legacy dimensions. Do not collapse them into one role enum.

## Observed login and account flows

1. `Auth::routes()` registers framework authentication routes. GET `/register` is later overridden to `HomeController@index`; this does not remove the POST route generated by the framework.
2. POST `/ssi/login` calls `customLogin`, validates email/password, looks up the user, calls `Auth::attempt`, then sends applicants to the named careers route and employees to the intended SSI route. It distinguishes unregistered email and incorrect password, and returns exception messages to the page.
3. The custom login action does not explicitly invoke the trait's throttling/session regeneration flow or enforce archive/termination eligibility. Verify effective behavior before porting; the target must implement both protections explicitly through the chosen authentication stack.
4. Framework POST `/logout` is used by the sidebar's CSRF-protected form. GET `/logout` points to `HomeController@index`; it is not the same logout action. `signOut()` exists but is not an explicit route in this snapshot.
5. `/ssi/login/{token}` decrypts an email, finds the local user, logs in using ID with remember enabled, and optionally redirects to a query value. It lacks explicit expiration/replay/redirect restrictions and does not handle an unknown account safely. Coordinate a new partner protocol rather than retaining those weaknesses.
6. HR/recruitment account creation and legacy reset helpers can set a fixed default password; self-service account editing can change email/password. Do not reproduce the default credential or mass reset endpoint in the replacement.
7. Default registration expects a `name` field while `users` stores separate first/middle/last names and required employment fields. Registration intent is unresolved (D03).

Legacy `LoginController::check_id`, `cancel`, and `compute` also implement time capture or DTR changes under guest middleware. They belong to the attendance compatibility review, not the target authentication domain. The `/index/check_last` route names an absent explicit method.

## Target permission model

Use named abilities and policies for each module. Suggested scopes to confirm with owners:

| Actor | Default target scope |
| --- | --- |
| Applicant | Own applicant account, documents, applications and eligible exam attempts |
| Staff | Own profile, requests, reports, notifications and permitted shared portal content |
| Division chief/OIC | Own employee access plus explicitly delegated, effective-dated division approval abilities |
| HR | Approved agency record/request administration and certification abilities |
| Payroll operator | Explicit payroll abilities; do not infer these from generic administration alone |
| ED | Explicit final approvals and approved agency overviews |
| System administrator | Account/configuration operations as granted; sensitive business approval rights require separate authorization |
| External service | Separate named client with the minimum device-ingestion or notification-publishing scopes |
| Public visitor | Login/password recovery and narrowly approved certificate verification only |

This table is proposed scope, not evidence of complete current enforcement. Implement model/child ownership, division and delegation checks at action level. Test lists, detail lookups, autocomplete, exports, batch routes and files as well as writes.

## Data and integration migration

Retain account-to-person IDs or a durable mapping; migrate usable password hashes only after checking the selected hashing driver and compatibility. Users without usable credentials require an invitation/reset flow. Avoid changing existing hashes by applying the hash operation twice. Invalidate legacy sessions at cutover according to the plan; session continuity is not assumed.

Preserve role codes in migration evidence while mapping to approved abilities. Email changes need a reviewed synchronization plan because legacy SSI and notifications resolve email. Keep service credentials separate from human accounts and scope attendance vs notification producers independently in the target.

## Build checklist

- [ ] Resolve D02/D03/D04 and specify account eligibility, applicant onboarding, role mapping, partner login and reset policy.
- [ ] Implement one primary login flow with throttling, generic credential errors, session regeneration and secure cookies.
- [ ] Implement logout with session invalidation and CSRF token regeneration; retire ambiguous GET logout behavior deliberately.
- [ ] Implement account invitation/reset, password confirmation where needed, and explicit email verification policy.
- [ ] Protect role, division, pay and signature attributes from self-service mass assignment.
- [ ] Add policies for every module, scoped record queries and effective-dated delegation rules.
- [ ] Map or retire generated registration/verification routes explicitly; close unintended registration paths.
- [ ] Implement audited account creation, role changes, archive/termination eligibility and secure password setup.
- [ ] Implement partner login through the accepted integration adapter; reject bad/unknown/expired/replayed credentials and unsafe destinations.
- [ ] Replace shared broad API credentials with approved service identities/scopes and rotation procedures.
- [ ] Remove fixed-password/mass-reset utilities and move guest attendance compatibility routes to their reviewed service boundary.

## Acceptance checklist

- [ ] Applicants and employees reach the correct destination; intended destinations cannot bypass access policies.
- [ ] Repeated failures are throttled and error responses do not reveal account existence or database exceptions.
- [ ] Sessions rotate on login, invalidate on logout, and cannot be reused after required revocation.
- [ ] Archived/terminated users follow the accepted account-access policy; role changes take effect without a stale authorization cache.
- [ ] Staff cannot change their own role, edit another account or obtain a foreign record through a guessed ID.
- [ ] Division/OIC access works only for the accepted organization and effective dates; moving a person does not rewrite historical approval authority.
- [ ] Direct POST registration follows the chosen onboarding policy even when its UI link is hidden.
- [ ] Partner login tests cover query/base-path encoding, unknown email, tampering, expiry/replay and blocked redirects.
- [ ] Service tokens authorize only their intended endpoints; revocation and secret rotation are demonstrated.
